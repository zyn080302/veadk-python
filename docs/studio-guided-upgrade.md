# Studio 指导升级版本发布

旧 Studio 会用自身固定的 AgentKit CLI 摘要检查完整升级包。当前 `20260917223852` 已核验的实现要求 CLI `0.52.19`；通道中的 `.14` 兼容运输包会在安装新更新器之前被拒绝。

过渡包应保留源校验器接受的原始 CLI 归档，安装按目标 wheel 合同验证依赖的新更新器。第一次由用户在原页面手选适用的过渡版本，此后可继续普通升级。保留完整包、wheel 和 CLI 的摘要校验，不以版本字符串代替实际摘要。

## 保持正常升级

旧页面会将目录按日期版本降序排列，并默认选择第一项；只保护 `latest.json` 不够。专用过渡包不能成为目录第一项。

发布过程必须先在隔离通道验证普通包和过渡包。过渡包的日期版本须大于适用源版本、小于配套普通版本；两个版本号均在实际候选生成时分配，不倒填历史版本。普通包必须保留原默认入口所需的历史 CLI 合同，并通过真实历史消费者及安装启动验收。

完成全部门禁后，先按普通流程发布已经验证的普通版本，再调用 `StudioReleaseStore.publish_guided(bundle, manifest, source_version=...)` 添加专用过渡版本。此入口不写 `latest.json`，不改变目录第一项，不覆盖历史对象，不淘汰已有目录条目；目录用 ETag 条件写入，发生并发变化或容量不足时停止。写入响应丢失时先回读，不重复提交。

## 验收与指导

- 原 `.19` 校验器应稳定拒绝 `.14` 入口包，并接受 `.19` 过渡包；原 `.14` 普通入口保持通过。
- 新更新器覆盖完整包、薄包及同目标完整包回退，包括 CLI 摘要变化；不能只测模拟 HTTP 成功。
- 使用未经预修补的旧页面手选过渡版本，完成依赖安装、发布和流量接管后，再从页面升级普通版本。
- 已保留 `.14`、`.18`、`.19` 真实历史源码与固定归档回归；缺少原实现的 `.15`–`.17` 保持未验证。
- 只有真实发布并核验目录可见后，才向用户给出可升级的准确日期版本号。构建候选号不等于可升级版本。
