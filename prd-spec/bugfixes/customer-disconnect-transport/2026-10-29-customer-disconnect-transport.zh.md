# 已确认断连被报告为通信失败时的恢复

[English](2026-10-29-customer-disconnect-transport.md)

变更 ID：customer-disconnect-transport。日期：2026-10-29。状态：用户明确要求修复停止单次查询后的同会话续聊，已授权本地实现与验证；仍禁止部署。

组件：[客户 Runtime](../../../specs/runtime-customer/README.zh.md)。前置设计：[确认取消](../customer-confirmed-cancellation/2026-10-29-customer-confirmed-cancellation.zh.md)。

## 证据、目标与范围

应用观测到模型执行中断后同一业务 Session 两次被恢复保护拒绝。用户确认停止了单次查询，但未关闭 Session。线上 Trace 尚未证明首次内部异常的具体时序。`runtime.py` 只有 `CancelledError`/`GeneratorExit` 会进入确认和收尾；通信层报告 `transport_error` 时，即使可信应用已独立观测到断连，也会跳过该路径。

通过稳定回归修复通用机制，保留原始错误、所有者身份、日志与停止证明。不改变公开 HTTP API、Session ID、数据结构、模型、重试策略、默认配置或旧 blocked Session。不强行解锁、不按 TTL 接管、不重放工具、不部署。

## 要求与场景

- FR-1：仅错误码精确为 `transport_error` 的 `CustomerChannelError`，可在 Dispatcher、工具、HTTP 和 journal 清理后进入既有可选服务端 `confirm_cancellation`。通信错误本身不能作为停止证明。
- FR-2：该回调必须独立确认真实断连，封锁并停止精确远端所有者，完成历史收尾。仅字面值 `True` 加上既有 journal/display 验证，才允许同身份下一轮执行。
- FR-3：中断请求保留原通信错误。回调缺失、False、非布尔值、异常，以及其他通信错误码、未停止任务或历史冲突，均继续保护会话。
- FR-4：保留用户输入和完整证据、恰好一个中断终态、工具调用配对和稳定远端绑定。不得重放旧工具或额外调用模型修复取消。
- FR-5：成功请求不增加回调、网络或存储操作；取消收尾继续受既有限时约束。证据不包含凭据或生产载荷。

## 设计与组件影响

扩展既有异常处理，只额外接受精确通信错误分类；其他 `CustomerChannelError` 立即继续抛出。复用现有清理和 `_settle_cancellation`，不增加恢复 API 或回调。应用已有可信确认回调在没有服务端断连标记时会拒绝确认。尝试收尾后始终继续抛出原异常。

本变更调整 CON-4/CON-5 可进入确认的失败出口，保留确认、隔离和持久化要求。不改变通信或存储数据结构。只检查任务取消计数不足以解决问题：通信读取和 Runtime 消费可能属于不同任务。把全部网络错误视为健康或删除锁会破坏所有者边界。
